# 中海物业新系统重建与分阶段迁移方案

方案按拿不到供应商源码设计。采用新旧并行、分批迁移的路线：旧系统继续办理未切换业务，新系统先建立数据与维护基础，再以项目和业务域为单位承接业务。每张单据在任一时刻只有一个办理系统，历史数据迁移和业务切换分开验收。

业务连续性的目标是客户受理和紧急服务持续可用。后台切换可能存在经过演练的短暂办理窗口，通过持久化受理队列或可追踪人工受理承接请求。只有在入口控制、数据同步和现场演练均得到验证后，才能给出具体中断时间承诺；目前不承诺所有场景技术上零停机。

这是一份实施建议，尚未操作生产系统。源码不可得不代表数据库、备份、导出、设备或对接账号一定不可得，这些能力在第 0 阶段分别核实。新平台应建立独立、由公司控制的代码库；本目录保存方案与旧系统分析依据。

## 一 现有证据与重建边界

| 已有材料 | 可以用于 | 还不能证明 |
| --- | --- | --- |
| 当前账号 9 模块 79 个入口和 285 条按钮权限定义 | 功能范围、入口对应、权限讨论起点 | 其他角色完整功能、后台逐接口权限 |
| 全部入口 HTML 和部分已执行加载的前端代码 | 字段、候选操作、状态分支、接口参数、界面行为 | 后续编辑页完整规则、全部后台状态迁移 |
| 初始化实际请求及星海图大屏补采 | 已观察读取契约、依赖和指标绑定 | 全部查询组合、写入正确性、后台算法 |
| 约 5 年实际运行背景 | 需要保留业务连续性和历史可追溯性 | 数据规模、历史完整性、附件总量、接口服务约定 |

现有采集材料是功能证据，不是五年业务数据备份。不能把页面导出的当前列表当作完整历史，也不能把旧前端隐藏按钮当作新的服务端授权规则。详见 [原系统分析总报告](../analysis-report.md) 和 [79 个功能分析](../features-analysis.md)。

新增需求使用 [业务词汇](CONTEXT.md)。报事事件、工单和待办任务分别建模，客户、员工和系统用户分别识别；已有代码确实使用不同身份与状态，但它们的完整关系仍需要业务人员确认。[服务调度证据](../service-dispatch-findings.md) 是这一设计的依据。

## 二 无源码条件下的实施路线

新系统建立公司自己的工作入口，通过明确的业务归属提供新模块和旧系统入口。能控制原域名或入口时再配置路由；不能控制时，使用公司新域名和明确跳转，保留旧系统原登录流程。未验证的会话、令牌和私有接口不能成为长期唯一依赖。

渐进替换有助于降低一次整体重写的切换风险，但经典代理式替换需要能拦截请求，部分方式还需要修改旧系统内部调用。没有源码时，本方案采用外部入口和运营范围的分批迁移，不假定可以在旧系统内部自由替换模块。[Microsoft 渐进替换模式的适用边界](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig)

| 数据能力 | 迁移办法 | 实施边界 |
| --- | --- | --- |
| 有数据库备份或只读访问 | 在副本上识别结构、全量抽取、关系校验；经授权且具备条件时读取变更日志 | 不直接向旧数据库写新业务，不依赖未知触发器或存储过程实现新系统 |
| 有稳定且允许使用的接口 | 按项目、实体和时间分批读取，保存游标、来源和版本；验证增量、删除及附件能力 | 现有 66 个初始化 XHR/Fetch method/path 组合只是观察起点，不能按名字推定只读；需单独验证分页、范围和接口稳定性 |
| 只有系统导出 | 按范围和期间归档原始文件，建立字段映射、重复检测及多批次对账 | 部分旧导出不包含全部筛选字段，不能假定与页面查询一致；变更历史和已删除记录可能缺失 |
| 只能浏览页面 | 在授权账号范围内做受控只读采集，并用业务台账交叉核对 | 不能承诺完整历史迁移、分钟级增量或自动回退；无法取得的资料保留缺口登记和旧系统查询入口 |

不能提取但仍需保留的历史，先提供可用的旧档案查询或独立离线归档。没有可靠数据通道时，可以上线严格限定范围的新业务试点，但旧系统退役必须等待历史保留条件满足，或业务负责人明确接受无法补齐的数据范围。

### 第 0 阶段必须消除的不确定项

| 尚未核实的条件 | 对计划的影响 | 处置与停止条件 |
| --- | --- | --- |
| 旧系统托管位置、可用期限、许可证、备份与故障恢复能力 | 分批迁移依赖旧服务在过渡期持续工作 | 先落实过渡维护、联系人和恢复演练；期限不足时缩小首批并优先受理及数据保全，不能把旧服务可用视为默认保证 |
| 数据及附件的来源、体量、一致性与抽取权限 | 决定历史完整性、同步方式、演练耗时和存储预算 | 用代表性抽取测量；不能确认范围的数据不宣称已完整迁移 |
| 其他角色功能与业务状态规则 | 79 个入口可能只是当前账号范围 | 补齐客服、处理人员、管理者及客户侧关键场景；未确认的状态和权限不开放写入 |
| 客户与员工终端、二维码、域名及回调的控制权 | 决定是否能按项目阻止旧系统接收新单 | 不可控入口所在业务暂缓切换，或先建立经验证的统一入口 |
| 财务、支付、票据和设备对接的账号与契约 | 决定 P4/P5 能否独立替换 | 无可靠对接和验收环境时保留对应旧链，不用页面操作拼出资金或设备控制能力 |
| 维护团队、预算与支持周期 | 决定技术选型及参考周期是否成立 | 指定长期负责人并确认投入，第 0 阶段重估排期与运行成本 |

若旧系统发生事故，先使用已有旧服务恢复能力和经过演练的备用受理流程。仅取得业务数据备份不代表可以重新启动供应商软件；运行包、许可证、配置和外部账号的可恢复性要分别验证。

## 三 新系统业务和技术结构

### 业务边界

| 新业务域 | 主要内容 | 数据责任和关键约束 |
| --- | --- | --- |
| 组织和身份 | 组织树、项目、服务中心、员工、系统用户、角色 | 服务端按组织和项目授权；员工身份与账号分开；跨项目管理人员需要明确范围 |
| 客户和房产 | 客户、房产、住户关系、历史变更、一户一档 | 保留有效期间；电话、展示房号不能作为唯一身份；与现有主数据系统明确唯一维护责任 |
| 客服和工单 | 报事、派单、执行、验收、回访、评价、投诉、待办 | 事件与工单分离；操作、权限和状态迁移均在后端校验；未知状态不能自动转为已完成 |
| 社区运营 | 公告、便民电话、活动、问卷、社交、工作计划 | 发布、停止、审核、通知分别记录；活动如有关联订单或收费，随交易域核验 |
| 装修和品质 | 申报、巡查、整改、发函、质检点位 | 保留通知与附件、整改闭环、责任人和原始时间；状态变化可追溯 |
| 访客和设备 | 预约、授权、通行、门设备、电梯、推送 | 历史记录迁入不授予通行权；设备实际控制独立验收，未切换设备继续由原系统管理 |
| 费用和交易 | 费用、支付、代扣、抵扣券、积分、减免、发票、交易 | 账务事实与支付交易分离；原支付和票据身份保留；导入历史不得触发扣款、兑换或开票 |
| 查询和统计 | 专题查询、专题报表、效率和大屏 | 指标定义有版本与适用期间；旧报表快照保留原口径，新旧数据混合时显式区分范围 |
| 平台支撑 | 文件、通知、审计、集成日志、数据迁移 | 文件权限跟随业务对象；消息和外部动作有去重、重试和投递记录 |

新状态机先用脱敏样本和业务工作坊确认。旧字典中的待派单、待处理、处理中、待验收、待评价和已完成只是已观察标签，不能直接当作完整迁移顺序；退回、重派、合并、撤销、超时和跨项目协作需补齐。

### 初期架构

采用边界明确的模块化后端、独立前端、关系型主数据库和公司控制的文件对象存储。迁移作业、统计处理和通知作业独立运行。跨模块通过明确接口交互，旧系统适配层统一处理旧字段、字典、错误与格式；旧私有接口变化不能散布到全部新业务代码。

后端为主要业务保持事务边界。需要可靠外部投递时，业务提交与待投递任务在同一事务保存，后台按幂等键执行并记录结果。缓存不作为单据、账务或受理请求的唯一存储；报表读取模型应保留数据时间和来源范围。

开发、测试、迁移演练和生产环境分离。数据库结构变更由版本化迁移管理，发布包可复现、可回退，接口契约和错误模型统一。前端采用有类型约束的工具链和统一组件体系，后端框架、数据库产品及托管方式在第 0 阶段按维护团队能力和支持周期选定，不凭旧界面决定新选型。

架构建议见 [业务切换责任决策](docs/adr/0001-project-domain-write-ownership.md) 和 [业务核心结构决策](docs/adr/0002-modular-core-and-isolated-legacy-adapter.md)。确有独立扩容、发布或责任团队需要的模块，再按这些边界拆分。

## 四 业务连续性和新旧并行

### 单据归属

| 对象或动作 | 切换前 | 切换后 |
| --- | --- | --- |
| 该项目该业务域的历史已结单 | 旧系统保存 | 新历史库只读查询，原证据可回查 |
| 切换时仍未结的旧单 | 旧系统继续办理 | 默认在旧系统办结，新系统提供带来源的查询或跳转 |
| 切换后新建的单据 | 尚无新单 | 新系统受理和办理，旧入口必须不能再接收同范围新单 |
| 旧系统仍维护的主数据 | 旧系统或既有主数据平台 | 新系统读副本或适配读取，不能同时提供另一套自由修改入口 |
| 未切换费用或门禁能力 | 原系统控制 | 仍由原系统控制，接入状态在新入口中明确显示 |

跨系统统一待办可以聚合查询，但要显示办理系统、来源单号、当前责任人和跳转入口。无法实时查询旧待办时，以可校验的每日未结单清单支持现场管理，并标注数据时间。读副本的状态不是业务权威状态。

同一个项目不能让 APP、小程序、呼叫中心和后台各自自由选择新旧工单。需核实所有上游入口、后台入口、定时任务和回调的归属。若某个入口不可分流，相关业务整体暂缓写入切换；仅隐藏旧菜单或通知员工停止使用不构成技术隔离证明。

客户房产等共享主数据比工单更难分批。新系统接管维护前，确认仍在旧系统办理的单据如何读取所需资料：可使用经验证的兼容同步，或在旧未结业务结束后整体移交；适合单据快照的字段由业务确认后保留快照。没有可靠兼容方式时继续由旧系统或既有主数据平台维护，新系统只读，不能先关掉旧维护再让旧单依赖过期资料。

### 客户与员工终端

现有证据以管理端为主，客户 APP、小程序、员工移动端、电话受理和印制二维码需单独盘点。如果旧终端代码和发布账号不可得，新平台要提供公司可发布的新终端或可用网页入口，并安排客户与员工切换支持；此项工作纳入重估，不能只重建后台页面就视为替换完成。

保留旧终端办理旧单、未切换业务和既有有效授权的路径。新旧单据查询与办理提示应清楚，切换通知、现场培训和客服指引按项目发放。不能升级的旧客户端若仍能创建同范围新业务，就继续阻止该范围切换；扫码和回调地址逐一核验，业务开始使用的新入口必须由公司长期控制。

### 首个试点

先选择一个业务负责人可参与、入口可控、主数据完整的城市范围内 1 至 3 个项目。初期可先上线便民信息或公告管理验证运维，再在同一受控范围验证完整客服工单链。试点包含客服、管家、处理人员、项目主管与城市管理人员的权限和交接。

试点新单全流程在新系统闭环，旧未结单继续在旧系统完成。未核实的收费维修、跨项目派单、外部地产处理等分支不加入首批开放范围；这些原有业务仍通过保留入口办理，不因试点被取消。新旧统计分别展示，待口径和历史映射确认后再合并。

### 受理与通知

如切换期需要暂停后端办理，只有经过演练的持久化受理能力才能承接请求；受理回执明确表示待登记或待分派，不能冒充已在旧系统建单。无法控制原客户入口时保留原办理链，使用人工受理清单应记录唯一编号、时间、联系方式、项目和后续办理责任，避免口头交接。

通知、设备指令、扣款、发票等外部副作用只由负责该业务单据的系统执行。只读并行计算不能真实发送通知或触发交易。消息关联业务单号与投递幂等键，重试、失败和人工处理都可追踪。

## 五 分阶段实施和退出条件

以下周期是预算讨论用估算。基线假设为约 7 至 9 人核心团队、能稳定取得必要数据、旧服务在过渡期间继续可用、业务负责人可按周参与。数据库权限、历史体量、外部接口和终端控制尚未核实；第 0 阶段结束必须重估，不能将估算当作交付承诺。

| 阶段 | 参考窗口 | 交付结果 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| P0 资产和规则摸底 | 第 1 至 2 周 | 数据访问分级、业务场景清单、数据样本、集成和账号清单、旧服务可用期限 | 数据获取路径可演练；试点入口可控；关键业务负责人明确；不可得资料有范围登记 |
| P1 工程和身份基础 | 第 3 至 6 周 | 公司代码库、部署流水线、组织和账号模型、后端权限、审计、文件、迁移框架、测试环境 | 可重复部署；跨项目越权测试通过；备份恢复演练通过；至少两人能独立发布和处理故障 |
| P2 历史查询和只读并行 | 第 5 至 10 周 | 首批客户房产副本、历史归档、只读查询、指标口径库、数据对账 | 试点所需主数据和关联完整；关键历史可查；统计差异有解释；旧库仍是对应业务权威来源 |
| P3 低耦合模块与工单试点 | 第 9 至 16 周 | 内容类模块试点、受控项目新工单全流程、统一待办和通知隔离 | 全渠道归属有效；新单不重复不丢失；旧未结单有办理路径；连续约两周满足业务与性能指标 |
| P4 服务和设备周边扩展 | 第 17 至 28 周 | 更多项目工单，客户房产主数据维护切换，装修品质、访客与设备接入 | 每批数据和外部依赖验收；设备实验与现场测试通过；无共享主数据双写；恢复流程可用 |
| P5 交易和复杂对接 | 第 21 至 36 周 | 费用、代扣、发票、抵扣券、积分、减免及收费活动等 | 同币种同期间对账完成；交易幂等与回调已验证；历史导入无副作用；至少两个完整业务账期验证 |
| P6 历史封存和旧系统退役 | 第 37 至 48 周或更晚 | 全部保留业务迁出、旧未结单处置、独立历史查询、供应商退出和长期维护交接 | 无业务写入和必要回调依赖旧系统；历史可保留可恢复；剩余缺口已明确处置；维护团队接管 |

阶段允许重叠，但业务切换依赖不能省略。首个受控工单试点约 10 至 16 周、主要模块约 6 至 9 个月、全部退役约 9 至 12 个月或更长，均受数据和对接能力影响。若只有页面访问，完整退役时间目前无法可靠估算。

[79 功能分批映射](feature-wave-map.md) 将每个入口分配到建议批次，保留暂时依赖和不应提前开放的分支。批次表示最早进入相应上线计划，并不保证该功能已具备切换条件。未使用功能应由业务确认继续保留或封存，不能仅按访问量低就删除。

## 六 历史数据策略

历史按三类处理：支撑当前办理的主数据和未结事实、需要高频查询的已结历史、低频原始档案。近期热数据期间由实际使用情况决定，五年历史不必全部变成新系统可编辑业务单据；原始记录、附件和对应编号应持续可追溯。

采用原始保留区、映射校验区、新业务及历史查询区三级处理。所有批次保留来源、抽取范围、时间、文件摘要、版本、原始编号和校验结果；转换规则升级不覆盖原始资料。迁移作业可以重跑、续跑和撤销未发布批次，异常记录进入隔离清单。

客户与房产关系、事件与工单、支付与发票必须保留关联。缺少明细历史、附件、已删除记录或状态轨迹时，标明缺失，不根据当前列表补造历史。当前已有导出行为与列表筛选不完全一致的证据，须用独立控制总数和业务台账验证抽取范围。

每批分别对记录身份、数量、关联、关键状态、附件和金额核验。金额按业务批准的精度以精确数值处理，按币种、期间、项目和状态对账；关键状态和迁移范围内金额差异须为零，差异解释与处置逐条保留。一般字段缺失如获准保留，也要在查询界面标注数据质量，不能把缺失记录从分母中悄悄排除。

完整步骤、来源分级、身份映射、增量限制、验收门槛和回退流程见 [历史数据与切换手册](historical-data-and-cutover.md)。

## 七 每批切换与回退

切换前完成至少两次范围相同的演练，记录抽取耗时、增量延迟、导入耗时和恢复耗时。制定人员、步骤、时限、检查结果及停止条件明确的切换手册；这与官方迁移实践中的演练和职责要求一致。[AWS 切换前准备](https://docs.aws.amazon.com/prescriptive-guidance/latest/best-practices-migration-cutover/pre-cutover-stage.html)

| 时点 | 可采用的恢复方式 | 禁止误判 |
| --- | --- | --- |
| 新系统尚未接收业务写入 | 撤销该批次入口变更，恢复旧受理；保留未发布迁移批次用于复查 | 历史导入存在不代表已发生新业务交易 |
| 已受理新单但尚未外部执行 | 停止后续处理，保存新单和受理清单；回退新应用版本或前向修复 | 不能让旧系统重新收同一批单而丢掉新单身份 |
| 已发送消息或发生交易及设备动作 | 以事实账本核对外部结果，再按对应业务规则处理；新数据继续由新库保存 | 数据库回滚不能撤回消息、扣款、票据或设备指令 |
| 需要将新业务重新交旧系统 | 仅在旧系统存在经过验证的导入或办理接口、字段映射与重放演练时执行 | 没有源码且没有可靠回写能力时，不承诺自动回切 |

切换后产生新交易，再把请求指向旧数据并不能恢复正确业务状态；恢复策略必须包含新增数据处理。[AWS 关于带新增数据的回退](https://docs.aws.amazon.com/prescriptive-guidance/latest/best-practices-migration-cutover/cutover-stage.html)

发现已确认单据丢失、重复业务执行、项目越权、无法解释的资金差异或关键受理故障时，立即停止扩大批次并隔离影响范围。可疑时先暂停相应外部动作，保全单据、日志和队列；仅在已验证条件下恢复旧写入。客户受理采用该批次已演练的备用路径，故障负责人同时明确修复责任和恢复顺序。

## 八 验收目标和持续维护

### 上线验收

以下为建议初始验收目标，P0 根据实际峰值、可用窗口和业务要求定稿。

| 维度 | 验收要求 |
| --- | --- |
| 单据连续性 | 已确认受理的单据可追踪，重复办理为零，试点旧未结单办理路径完整；每张单据均有归属 |
| 数据 | 范围内主键身份和关键关联完整；关键状态与资金对账无未解释差异；附件缺口有清单 |
| 权限 | 服务端执行角色和项目范围校验；跨项目、跨组织、批量导出和附件访问的负向测试通过 |
| 外部对接 | 回调重复、乱序、超时和重试有处理结果；没有两套真实通知或交易执行 |
| 容量与体验 | 用实测峰值和典型大查询做容量验证；不得只以单用户演示通过验收 |
| 恢复 | 建议普通业务起始目标为故障恢复不超过 60 分钟、灾备数据恢复点不超过 15 分钟；已确认业务受理另要求持久化和重放验证，不能用普通备份目标解释丢单 |
| 运维 | 监控受理、队列积压、业务失败、增量延迟、回调和备份；报警有当值责任人，恢复演练记录可查 |

生产数据恢复目标与维护窗口最终由业务、数据和运维负责人共同核定。收费和设备业务如果达不到相应安全恢复要求，保持在原系统，不因其他模块上线而提前切换。

### 公司拥有和交接的资产

源码、代码库组织、构建配置、制品、数据库结构和迁移规则、运行手册、域名、部署账号、对接账号和证书必须由公司掌握。生产密钥在受控密钥管理中保存，不放进代码库；供应商或外包以限定协作权限参与，离场不会使构建和部署中断。

交付按功能、数据、对接、部署和恢复能力验收。至少两名内部或公司长期控制的维护人员能独立从代码库构建、部署、恢复备份和定位常见故障，不能只验收安装包或在线演示。不得把所有业务规则藏在无法交接的低代码配置或第三方私有组件中。

### 维护节奏

| 频率 | 责任与活动 |
| --- | --- |
| 每日 | 运维检查业务错误、受理积压、备份结果、同步延迟；业务检查未处理异常与跨系统遗留单 |
| 每周 | 数据负责人处理对账和迁移异常；产品确认规则变更；开发和测试复核近期事故与高风险改动 |
| 每月 | 按风险评估依赖和安全补丁，检查容量、存储、证书到期和成本，发布小规模维护版本 |
| 每季度 | 做备份恢复和关键流程故障演练，检查越权测试、集成替代能力及旧适配依赖退出进度 |
| 每年 | 复核框架支持周期、技术债、关键人员交接和业务口径，制定下一年度维护计划 |

开发变更应包含契约或业务场景验证、数据库升级步骤和恢复条件；规则变化先更新需求与指标版本，再修改实现。维护工时和运行成本单独编入年度预算，覆盖托管、存储、消息、备份恢复、补丁和业务小改动；不能只采购一次性开发交付。

技术负责人维护依赖清单、版本及支持截止时间，在停止支持前安排升级。核心业务规则、接口契约、指标口径、数据字典、故障手册和历史转换规则随代码版本交付；维护人员通过真实恢复和故障练习完成交接。供应商离场时还需撤销其访问权限并核验公司仍能独立构建、发布和恢复。

## 九 团队责任和首两周任务

核心团队建议包含业务产品负责人、技术负责人、2 名左右后端开发、1 至 2 名前端开发、测试人员，以及数据迁移和运维能力。数据和运维可部分共享，但负责人与投入时间必须明确。交易、设备和移动端接入时，另安排业务及对接团队参与。

| 前两周任务 | 主要负责人 | 明确产物 |
| --- | --- | --- |
| 核实数据库备份、只读库、接口、导出和附件访问 | 数据负责人及现系统管理人员 | 数据能力等级和缺口列表，代表性抽取试验 |
| 核实域名、APP、小程序、呼叫中心、企业微信、设备和回调归属 | 技术及业务负责人 | 所有入口和对接的所有权及切换能力清单 |
| 固定业务术语、典型流程和异常分支 | 产品与现场人员 | 约 20 个首批关键场景及真实脱敏样本，状态与权限待确认项 |
| 测试一个项目的数据关联和抽取范围 | 数据与测试 | 客户房产、事件工单、未结单和附件的样本对账 |
| 选择受控项目和确定旧服务保留条件 | 项目及城市业务负责人 | 试点边界、办理人、旧系统有效期限和备用受理方式 |
| 确定维护团队与技术选型 | 技术和运维 | 可复现环境、候选框架支持周期、公司资产清单与投入估算 |
| 形成阶段预算与交付边界 | 项目负责人 | 重估周期、试点验收条件、依赖和延期处理办法 |

第 0 阶段的最小决策是：哪些数据真正能拿到，哪个项目的全部入口可以控制，以及谁能够长期维护新平台。三者明确后，进入身份基础、只读历史查询和首条业务链开发。
