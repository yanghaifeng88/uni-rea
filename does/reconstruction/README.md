# 新系统重建与迁移方案

按无法取得供应商源码的前提编制，依据当前账号的 9 模块、79 个入口分析。以下内容都是实施建议；数据权限、终端控制、后台业务规则和维护投入尚需第 0 阶段核实。编制日期为 2026 年 10 月 14 日。

建议先阅读总体方案，再用功能映射组织业务评审，数据与切换手册用于迁移演练。

| 文件 | 内容 |
| --- | --- |
| [总体方案](rebuild-migration-plan.md) | 无源码路线、业务结构、不中断受理、分阶段排期、验收、回退及长期维护 |
| [79 个功能批次映射](feature-wave-map.md) | 逐入口建议阶段、关联依赖和开放条件；全部 79 个菜单身份保留 |
| [历史数据与切换手册](historical-data-and-cutover.md) | 数据来源、身份映射、全量增量、对账、切换时间表和故障恢复 |
| [业务词汇](CONTEXT.md) | 客户房产、事件工单、任务、交易与指标等概念的边界 |
| [单据办理责任决策草案](docs/adr/0001-project-domain-write-ownership.md) | 项目与业务域分批切换，每张单据只有一个办理系统 |
| [业务核心架构决策草案](docs/adr/0002-modular-core-and-isolated-legacy-adapter.md) | 模块化业务核心、独立迁移作业和统一旧系统适配层 |
| [结构化功能映射](feature-wave-map.json) | 供后续排期读取的菜单身份、原始名称、来源 URL 和建议阶段 |

第一步是用两周核实实际可取得的数据、一个项目全部入口的控制能力及长期维护责任。具备条件后先做基础平台和只读历史，再试点一条完整工单链；交易与设备在各自验收通过后切换。

历史未结单默认继续在旧系统办结，新系统负责切换后的新单。已有新业务写入后的恢复优先保留新数据库、回退应用或前向修复；回到旧系统办理必须另有经过演练的数据交接能力。

证据入口为 [旧系统分析总报告](../analysis-report.md)、[逐功能分析](../features-analysis.md) 和 [功能目录](../function-catalog.json)。当前材料是功能证据，不能替代五年业务数据备份；没有完整且独立可恢复的历史保存方案前，保留旧历史查询能力。
