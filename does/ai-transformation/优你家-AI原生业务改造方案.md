# 优你家 AI 原生业务改造方案（讨论稿）

编制日期：2026 年 11 月 10 日

依据完整清单复核：2026 年 11 月 10 日

## 一、项目目标

在老优你家底座持续运行的前提下，以功能平移清单中的高优先级业务为起点，逐步建设连接飞书、豆包工作与现有物业业务的 AI 能力。保留旧系统的业务数据、权限规则、状态流转和对外业务链路；在权限、接口和可靠性验证通过后，再逐项增加新的查询、表单、审核辅助和受控办理入口。

项目目标不只是让 AI 回答问题，而是让员工在原有授权范围内：查到业务、看懂上下文、用更少操作完成标准业务，并可以追溯每一次办理。高频标准录入优先使用普通表单；需要理解、跨单查询、归纳和生成草稿时再调用 AI，控制员工额度。

> 本方案是决策和试点讨论稿，不表示现有接口、身份传递、MCP 联调或生产写入已验证。

## 三、高优先级业务评估与实施顺序

清单中共有 20 条“高”优先级记录；“高”是业务重要性，不自动等同于先开放 AI 写入。每项均按“查看信息—准备办理—确认/审批—真实执行”拆分；实际工作量、频率和收益需要基线测量。以下先列员工移动工作台的六条，再列其他端的十四条。

| 清单高优先级业务 | 主要业务价值 | 建议首批可交付内容 | 后续开放条件 |
| --- | --- | --- | --- |
| 历史工单查询 | 减少跨页面、跨时间查找；服务人员接待客户时快速了解上下文 | 首个只读试点：按项目、客户/房屋、状态和时间查询；可查看来源、时间、状态及旧系统详情链接 | 核验分页、历史覆盖、权限、脱敏和状态口径；无权限或结果不全必须明确返回 |
| 公告公示审核 | 缩短查找待审公告和核对内容、范围的时间，降低遗漏 | 待审列表、公告内容/发布范围查看，AI 辅助检查和草稿建议；审批先回旧系统 | 核验审批角色、节点、状态、受众、发布时间、撤回及重复提交后，再评估受控审核 |
| 放行条审核 | 让审批人更快核对申请人、房屋、物品和放行时间 | 申请详情、待办查询和风险信息提示；复用旧系统完成审批 | 明确审批时效、物品/申请人规则、撤销、现场验证及门岗放行链；AI 不自行授权放行 |
| 业主卡审核 | 降低资料核对和补件沟通成本 | 申请列表、申请资料和房屋关系查询，辅助列出缺失项；最终审核暂在旧系统 | 核验申请类型、客户/房屋关系、附件权限、审核规则和卡片生效/撤销机制；不凭名称假定卡的技术形式 |
| 中海优行访客审批 | 方便审批人获取访客申请及项目、访问时间等上下文 | 已授权范围内查待办及申请详情；审批与实际通行先沿用旧链 | 先核验有效期、撤销、二维码/设备权限及各系统责任；历史记录不等于通行授权 |
| 零星收款 | 减少录入差错和收费信息查询时间 | 先核对收费项目、金额、状态和既有交易记录；是否可生成草稿需进一步确认 | 核验收款主体、渠道、订单/二维码、支付回调、重复支付、退款和对账；首批不直接触发支付或生成实际收款码 |

### 项目运营管理平台及优你家Plus的高优先级记录

| 端与清单功能 | 业务价值 | 建议实现边界 |
| --- | --- | --- |
| 项目运营管理平台：待办任务 | 汇总分散任务，帮助员工快速定位和处理 | 先按真实权限只读查询并跳回原工作台；不同业务类型的“详情/处理”可能带副作用，逐项验证 |
| 项目运营管理平台：公告公示 | 管理公告创建、审核、发布和状态 | 先查待审和查看内容；新增、审核、发布、受众和撤回按独立操作逐项验证 |
| 项目运营管理平台：社区活动 | 管理活动报名、名单、签到和结果 | 优先只读查看已有活动及报名；清单描述未证明活动创建/发布接口，前期原型只作设计设想 |
| 项目运营管理平台：客户管理—客户管理 | 快速了解客户和房屋关联，减少客服查询 | 先做最小字段的权限内查询；身份证、电话等敏感信息按需脱敏，编辑另行验收 |
| 项目运营管理平台：客户管理—房产管理 | 减少查找房产及基础信息的时间 | 先查项目、房号和基础档案；主数据修改须明确权威来源与责任人 |
| 项目运营管理平台：问卷管理—问卷结果 | 方便查看发布和填写情况 | 先展示原系统结果与范围，不擅自解释统计口径或去重规则 |
| 项目运营管理平台：问卷管理—员工受欢迎指数报表 | 辅助了解评价情况 | 先复用原报表并标明口径未知项；人员评价属于敏感业务，严格限制访问与传播 |
| 项目运营管理平台：问卷管理—问卷配置 | 减少问卷配置和维护工作 | 先查配置；生成二维码、发布、停用等分别核验授权和副作用 |
| 项目运营管理平台：管家关系配置 | 快速查询项目管理区域和责任管家 | 先查询对应关系；新增、修改、删除须核验归属和交接规则 |
| 项目运营管理平台：一户一档 | 聚合授权范围内的房屋与服务信息 | 以只读视图试点；客户信息权限、字段完整性及历史有效期须验证 |
| 项目运营管理平台：服务中心管理 | 方便查询项目/服务中心主数据 | 先查主数据；新增、停用、删除和跨系统同步留待专项验收 |
| 项目运营管理平台：用户管理 | 方便管理用户与职责交接信息 | 仅限定管理员查询；角色、权限、账号与交接修改不作为首批 AI 写入 |
| 优你家Plus：人脸录入 | 支持与既有门禁的人脸录入及下发 | 设备和敏感生物识别信息专项，先核验授权、合法性、下发、撤销、设备联动，不列入首批 |
| 优你家Plus：云对讲 | 支撑已有对讲能力 | 先核验设备协议、网络、权限和状态；不假定 MCP 本身可以承载实时音视频 |

跨端的公告公示、审核和待办应共享已核验的业务身份与状态，不应因清单有多条记录就建立多套独立业务。公告“发布”和活动“发布”在此前原型中已做概念演示；实际是否开放及原系统是否支持对应接口，需要业务负责人确认。

## 四、目标架构

```text
员工入口
├─ 飞书 / 豆包工作：自然语言查询、摘要、待办辅助
├─ 标准表单 / 业务页面：高频录入、核对和人工办理
└─ 旧优你家入口：保持原有办理与异常兜底
                │
                ▼
企业 AI 能力与适配层
├─ ReachAI：能力目录、编排、模型接入、可用治理与运行记录
├─ 老优你家适配层：接口/字段/状态映射、错误、分页、限流
├─ 身份与权限：飞书员工 → 旧系统账号 → 组织/项目/操作范围
└─ 对外能力：经验证和授权的 MCP 或其他受支持集成方式
                │
                ▼
老优你家业务系统及既有支付、访客、门岗等外部系统
```

**单一业务权威：** 试点期间，老优你家继续作为相关业务数据和状态的权威来源。新界面和 AI 不另建一套可独立办理的业务账本。各业务对象的真实提交、状态变化和外部副作用只能通过经过确认的原业务链路完成。

**旧系统无源码时的现实路线：** 优先供应商正式接口与测试环境；若只能使用已有页面依赖的内部接口，必须取得使用授权，逐项确认身份、状态、副作用、分页、稳定性和版本维护责任。可在企业控制的独立适配服务实现兼容，再按 ReachAI 实际支持的接入方式注册能力。不要假定必须修改老系统代码，也不能假定 ReachAI 的 SDK、页面动作或扫描能在无法改造系统时直接生效；如既无可调用接口也无可靠数据访问，只能做受限的历史资料查询或继续使用原页面，不能承诺实时完整或自动办理。

**豆包接入：** 先在真实企业租户中验证 ReachAI 对外发布的 MCP 与豆包工作所支持的传输、认证和工具发现是否兼容；不兼容时评估受控协议适配或飞书集成平台。图片中已有的飞书文档侧边预览可作为参考，但自建业务表单能否在同一位置展示尚未确认。

## 五、三类典型用户流程

1. **员工查询历史工单**：员工在豆包工作发起查询 → 鉴别员工身份与项目范围 → ReachAI 选择已授权只读能力 → 适配层查询旧系统 → 返回必要字段、查询范围、时间、分页/不完整提示和旧系统详情链接。需展示文档时，再验证飞书文档创建权限与预览方式。
2. **主管审核公告**：进入待审列表或对话查询 → 展示原始公告、受众和状态 → AI 可给出检查建议并注明依据/不确定项 → 审核人核对 → 第一期跳转旧系统完成审核；后续仅在审批链、身份、幂等和审计验证后考虑在新入口确认执行。
3. **员工发公告或活动**：业务负责人确认业务范围后，在标准表单填写项目、内容、受众、时间 → 人员预览和确认 → 经验证的旧系统发布能力执行并返回真实状态/单号。未验证前仅做草稿与原型，不实际发布或发送。

## 六、分阶段实施

| 阶段 | 参考周期* | 关键交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 0. 范围与技术核验 | 1–2 周 | 全部高优先级记录的流程、角色和接口证据台账；供应商授权、旧系统环境和运行期限；ReachAI 版本与飞书接入条件 | 明确可用测试账号、网络、接口、身份方案及第一批业务负责人；不可得项记录并调整范围 |
| 1. 工单只读试点 | 2–4 周 | 1–2 个项目、2 类角色的历史工单查询；ReachAI/适配层；豆包端工具联调；权限、分页、异常和审计 | 典型样本与旧系统核对一致；跨项目拒绝通过；出现异常能关闭新入口并继续原工作流 |
| 2. 审核辅助 | 3–5 周，可与阶段 1 部分并行 | 公告、放行条、业主卡和访客待办查询及审核辅助；人工仍在原系统决策 | 每个业务的实际授权、状态、附件、规则和跨角色对账通过；任何未验证副作用保持关闭 |
| 3. 受控办理及资金场景专项 | 单项另行估算 | 逐业务核验后的审核/办理或零星收款能力 | 经业务、系统、财务/设备责任方共同验收；重复调用、超时不确定结果和外部副作用有处置方案 |

*周期为讨论级估算，假设已有测试环境、供应商配合、可用接口、1–2 名业务骨干及约 3–5 名跨职能人员可按需投入；未测量，不能作为交付承诺。身份和 MCP 若需适配或旧接口不可用，需重新估算。核心路径预计 6–10 周用于完成只读试点与首批审核辅助的评估及实现，是否具备上线条件由验收决定。

## 七、上线原则与验收

- **身份和授权**：不能以提示词中的用户名、项目名或共享管理员账号当作权限依据。验证豆包/飞书的可信员工身份与旧系统账号映射；跨项目、离职、权限变更和会话失效必须测试。旧系统若不能可靠执行用户级授权，先限制试点范围并建立经批准的服务端授权映射，否则不能对多人开放。
- **副作用分级**：读取、草稿、提交、审批、收款、通知和通行授权分开；页面叫“详情”并不保证只读。审批/对外发布应确认或沿用原流程；涉及资金、设备和通行的动作另行验收。
- **可靠性**：接口超时不等于失败，写入需业务幂等键或等效去重、执行结果查询与人工对账。旧系统超时/限流时给出明确错误，禁止 AI 编造成功。重要操作支持关闭新入口，继续在旧系统办理；已发生的收款、通知、授权不能靠页面或数据库回滚抹掉。
- **数据**：对电话、房号、访客等按角色最小展示，限制传给模型和日志的字段；确认模型、ReachAI、飞书和第三方各自的数据处理、留存、跨境及访问权限。展示结果应标明业务范围、时间、来源和不完整信息。
- **试点评估**：先测旧流程基线，再对等对比：每单办理时间、步骤数、查询成功率、数据差异与漏项、跨项目越权拒绝、异常/重复办理次数、员工活跃使用率、AI 点数和每任务工具调用数。设定上线门槛需业务方确认，不能先编造节省比例。
- **运维与回退**：确定系统 owner、供应商联系人、接口和证书期限、错误告警、审计留存、权限变更、发布回滚与数据对账责任；ReachAI 与适配层异常时，员工可以回到旧入口继续办理。

## 八、建议立即确认的决策

1. **确定首试场景与项目**：建议选一个有代表性的项目，先做“历史工单查询”；由客服主管和项目主管各参与一种角色验收。
2. **确认旧系统接入条件**：是否有后端源码、正式 API 文档、测试环境、每人独立测试账号、供应商支持及允许接口集成的授权？现有材料不足以判断。
3. **明确豆包工作使用方式**：企业统一配置的工作伙伴，还是员工各自的工作台连接器？确认租户权限、认证方式、额度归属和自建 MCP 接入能力。
4. **锁定 ReachAI 试点版本**：确认部署模式、版本/提交、运行依赖、支持维护人；优先实测 MCP 发布、调用方身份和关键能力的端到端治理，不将项目宣传或开发状态等同于已在企业生产可用。
5. **确认全部高优先级业务责任人**：分别指定业务、系统及财务/门岗责任人，补充流程、频率、审批规则及例外情况。

**建议决策：同意先做“ReachAI + 旧系统适配 + 飞书/豆包工作”的历史工单只读试点；20 条高优先级清单记录都纳入范围，按跨端业务去重后分批实施；审批、收款、权限及设备控制按真实业务规则分期放开。**
